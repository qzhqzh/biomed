# 全文续跑的集合索引（2026-11-07）

全量元数据集合超过百万条后，全文阶段每步要统计已尝试数、定位下一条，以及汇总请求账本；仅有 `collection_id` 单列索引时，SQLite 仍需大量回表读取状态或流量字段。恢复阶段的 `metadata_version IS NULL` 检查也可能遍历整批元数据。这些是现有安全预算与断点逻辑的必要查询。

`0013_collection_hotpath_indexes` 只增加三个普通索引，不改资料、任务状态、预算、限速、知识或外键。

| 索引 | 字段 | 作用 |
|---|---|---|
| `collect_entry_fulltext` | collection、fulltext_state、id、reused、metadata_version | 已尝试全文 COUNT、页面按状态／复用情况汇总，以及恢复时缺元数据 EXISTS 都可使用覆盖索引；pending 按 id 续跑无需额外排序。汇总 GROUP BY 可以对索引中的窄值临时排序，但不回读宽资料行。PMCID 的 JSON 条件仍读取候选行，不宣称全文选择完全覆盖。 |
| `collect_fetch_budget` | collection、charged_bytes、wire_bytes、decoded_bytes、elapsed_seconds、state | 请求预算 SUM 和页面的次数、流量、用时、失败／预留数汇总使用覆盖索引，无需逐条读取含 URL、消息的宽行。 |
| `collect_fetch_started` | started_at | 每次请求查全局最后请求时间可逆序索引取第一条；也支持近 24 小时请求窗口过滤，避免全表排序。 |

累计 COUNT/SUM 仍与相应索引条目数相关；这次修复减少回表，不把累计预算改成可能失准的缓存。索引需要额外磁盘空间，创建期间 SQLite 会持有写锁，应择业务空闲时间执行并记录实际耗时。

恢复时的 `metadata_version IS NULL` 检查复用全文索引中已有的该字段。由于它位于后部，全部元数据齐全时仍需扫描该集合的窄索引来确认没有缺失；这是偶发恢复操作，不再为它单独建立第二个百万条索引，避免重复构建时的宽表读取和长期空间占用。此调整发生于 0013 尚未成功应用时；旧迁移不修改。

## 高频调用约束

- 独立监控只读采集主记录、当前任务和心跳，以持久化`phase/step`检测进度，不查询百万条文献计数。元数据已完成不能让后续全文阶段失去监控。
- 页面每15秒读取实时状态，文献数量与网络账本各有独立60秒缓存；`counts_as_of`和`metrics_as_of`显示统计时间。缓存命中不查询这两张表。手动展开分类详情时重新计算文献数，避免分类分子与旧分母不一致。
- 下载前的预算校验不读UI缓存；COUNT和SUM合并为一次覆盖索引查询，在原事务中预留预算。中断请求的预留仍计费，不能用缓存突破限额。
- 恢复时将总条目、已保存元数据、全文尝试和非pending数量合并成一次覆盖索引聚合，复用同一事务中的准确结果，不重复计数。
- 全局最后请求仅读取`started_at`，保持时间排序，使用索引取第一条；网络间隔不变。

文献摘要只按`fulltext_state`分组，复用元数据数量用条件COUNT；原先按`fulltext_state,reused`分组虽然可用覆盖索引，仍产生百万行临时分组B-tree。真实数据核验发现此开销后已取消，不能只看“使用索引”就认定查询已足够快。

后续新增轮询、后台调度或预算校验时，应先检查实际SQL、查询计划和现有数据规模，不在高频路径加入无界COUNT/GROUP BY或拉整行排序。优化需保留预算准确性和断点语义，不能仅放宽超时。定期精确统计与实时状态分别处理，缓存必须明确时间和边界。

## 现用 SQLite 的一次性应用

先保存当前运行状态，确认未并行执行其他数据库迁移。已经完成 0012 的运行库，可在已授权维护窗口使用：

```bash
docker compose exec -T web python - --max-seconds 1200 < scripts/apply_collection_indexes.py
```

脚本只接受该单步向前、原子、恰好三个明确 `AddIndex` 的计划；缺少前序迁移、已有同名索引但没有迁移记录、索引定义不符都会拒绝。它通过 Django 正式迁移并记录结果，不使用 fake。退出前在同一事务内检查原 schema 未变和三个索引的表、列、顺序、排序方式，再允许提交。

本次没有修改任何行或外键，因此迁移期间仅将 Django 的退出检查替换为上述精确 schema 核验，避免默认全库 `foreign_key_check`。仅影响当前专用 CLI 连接，结束后恢复检查方法和 busy timeout；不修改 journal 模式。失败关闭专用连接以回滚未提交 DDL，不应在同一失败 CLI 进程中继续业务操作。

锁获取等待最多 5 秒；SQLite VM 执行默认上限 180 秒，可用 `--max-seconds` 设置 1–1800 秒，超时回滚。每个索引开始／完成输出 JSON 进度，长操作约每 10 秒输出一次；最终输出 applied/already_applied 及耗时。不要在锁失败后无间隔循环重跑。

首次四索引尝试中，全文索引构建约 560 秒，第二个独立元数据索引开始后达到总计 600 秒上限；已确认全部回滚、没有迁移记录。上面的三索引版本移除了重复构建，并以实测耗时设置一次性 1200 秒构建窗口；不改变采集请求的限速、预算或超时。索引是否已实际提交应以应用日志及迁移记录为准。
